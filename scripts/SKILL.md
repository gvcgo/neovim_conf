# 专属工作流与开发规范 (My Workflow Guidelines)

在协助当前用户进行开发、代码审查或架构规划时，你必须严格遵守以下定制规则。这些规则的优先级最高，旨在保持项目的一致性、精简输出并尊重用户的绝对控制权。

## 1. 核心交互与规划行为

- **对话式规划**：绝对不要创建任何物理的 plan 文件（如 `plan.md`）。所有的计划、任务拆解和进度确认，直接在当前session中以对话的方式沟通确定即可。
- **禁止擅自安装**：未经用户明确允许，绝不能私自安装任何 SKILL 或插件。
- **强制等待确认**：在工作流中遇到任何不确定、面临多项选择或存在风险（如大范围重构、删除文件）的节点，**必须停下来等待用户的明确确认**，收到允许后才能继续下一步。
- **默认沟通语言**：在没有收到明确要求的情况下，始终使用**中文**回答和沟通。
- **克制与收敛**：在没有收到明确要求的情况下，按照项目中已有代码的传统进行思考和实现即可，**一定不要无休止地发散**、过度设计或引入不必要的新模式。

## 2. 代码生成与修改约定

- **关于单元测试**：在没有收到明确要求的情况下，**不要**写任何单元测试文件。
- **关于代码注释**：在没有收到明确要求的情况下，**不要**写任何注释。如果用户明确要求写注释，注释内容**一定要用英文**书写。

## 3. 特定项目规范：`inlight-board/backend/go`

当你在处理 `inlight-board/backend/go` 项目相关的任务时，必须严格遵守以下专属架构与代码风格要求：

- **风格对齐**：必须注意 Go 代码的规范和风格，尽量参考同一目录下或项目内已有的代码实现。
- **Helper 函数布局**：所有的 helper（辅助/工具）函数应该尽量放置在每个代码文件的**末尾**。
- **Swagger 文档规范**：
  - 文档目录设在 `inlight-board/backend/go/doc/` 之下。
  - **总入口**：`inlight-board/backend/go/doc/api.yaml` 是文档的入口文件。
  - **模块映射**：`doc/` 下其余的 `*.yaml` 配置文件命名，必须与 `inlight-board/backend/go/src/vibe/api/` 下的文件夹**一一对应**。在增加或修改 API 接口时，请确保在正确的 YAML 文件中同步维护文档。
